## 1. Architecture Decision

- **Context:** The spec fences this to verification: the deliverable is written evidence, not code, and NFR-1/NFR-2 hold every path outside `.spark/graph-mcp-verification/**` byte-identical (C12 removes even the README grant the prior sweep had). Three claims must be observed in environment states that cannot coexist in one session — a silent no-tool state, `runner=yes, graph=no`, a built graph answered over MCP, the same graph answered without MCP, and two browser-MCP sessions — while constitution §6 forbids unasked mutation, §3 forbids new tracked executable code, §4 forbids assuming a test suite, and §8 defines a performed step as a real ceremony invocation or an observed command output. A3/R1 is already realized, not hypothetical: `graph-gates`' own remediation put the runner on `PATH` machine-globally (`.spark/graph-gates/evidence.md`, Change 2: "*the negative venue no longer exists as a natural state on this machine*"), and this repo now also carries `.aspark-graph/graph.json`.
- **Decision:** One ledger, `.spark/graph-mcp-verification/evidence.md`, written run-by-run in task order, negative case first. It opens with a method header — the four-verdict vocabulary (`confirmed (performed)`, `confirmed (documentation-level)`, `refuted-with-finding`, `not-verified-live (venue named)`), the counting domain rule (ceremony-emitted output and produced artifacts only; loaded file contents never counted, AC-2.3), and a mutation log whose every row names authorization and restoration — and closes with a per-issue verdict table giving each AC exactly one verdict. **Four fresh disposable venues outside this repo, one state each** (`V-SILENT`, `V-HINT` = `runner=yes, graph=no`, `V-MCP` = source-indexed repo with a built `stale:false` graph, `V-PAGE` = a localhost static page), built this sweep, never reused from the prior one. **MCP registration is per-leg, project-scoped to its venue, and torn down before the next leg** — never one global registration for the whole sweep — because #8's control (AC-3.3) and #10's two backends (AC-4.4) are only independent if no other server was ever in the session. Nothing surfaced is fixed: findings quote the contradicting text verbatim with `file:line` and name their route.
- **Alternatives considered:**
  | Alternative | Why rejected |
  |---|---|
  | Reuse `graph-gates-verification`'s venues, registrations and August baseline | Its own record documents the machine-state change that invalidates it (runner now global), the `/tmp` venues are gone, and A3/R1 plus this repo's `CLAUDE.md` habit ("a disclosed limitation stays honest only if re-verified") make a month-old probe exactly the thing not to inherit. The only thing reused is *method*, cited, not *results* |
  | One evidence file per issue (`issue-8.md`, `issue-10.md`, `issue-11.md`) | AC-1.2's mutation log and AC-1.3's "silence case precedes every positive run" are cross-cutting; three files would triplicate the baseline and make the ordering claim unverifiable by reading. One ledger + a per-issue verdict table gives both the per-issue view and the order |
  | One MCP registration set, held for the whole sweep | Destroys AC-3.3's control and AC-4.4's independence: a session that once held `aspark-graph`/Playwright/Chrome DevTools MCP cannot prove the branch that assumes none. Per-leg registration costs sessions and buys the only thing the ACs ask for |
  | Fix inline whatever the sweep surfaces | Breaks the verify-only fence (spec §6, NFR-1/NFR-2): repair widens the diff and converts a refutation into a change. `CLAUDE.md`'s refuted-with-finding ceremony is the sanctioned outcome |
  | A scripted harness that runs the legs and emits transcripts | Constitution §3 — no new tracked executable code; and an untracked scanner buys nothing here, since every row needs a judgement (was this mention ceremony-emitted or loaded file content?) a parser cannot make. Hand-run commands quoted in the ledger are recountable |
  | Run the legs inside this planning session | MCP servers and plugin material load at session start; a zero-probe or MCP-branch count is only meaningful in a session whose registration state is known-fresh |
  | Trace `/demo-day`'s resolution logic only, and skip #10's live leg | C11 explicitly re-sanctioned the scratch-page workaround; a read-and-trace is `confirmed (documentation-level)` at best (AC-4.1) and §8 forbids counting it as a pass. Both are kept, labelled apart, never conflated |
- **Consequences:** Easier — the fence is auditable by `git diff --name-only`, every count is reproducible by re-count from a quoted command, and refutation, technical failure and missing venue each have a pre-built landing place, so no row has to be forced. Harder — many fresh sessions (real spend), strict teardown discipline between legs, and one venue state (`V-SILENT`) that requires a machine-global mutation, now authorized by the user (Q6, granted 2026-09-21) and bracketed by restore/verify probes.

## 4. Test Strategy

No automated suite exists and none is possible for prompt material (constitution §4); for this feature the ledger **is** the test suite, and the bar per task is constitution §8's performed step — a real ceremony invocation or an observed command output, never a read-and-reason. Three layers:

- **Layer 1 — command-level probes with captured output (T1, T3, T5, T8, T10, T11, T13):** availability probes, `claude mcp list`, `query staleness`, PyPI status, the fence and teardown checks. Reproduction = re-running the quoted command.
- **Layer 2 — ceremony-level runs in fresh sessions whose registration state is declared (T2, T4, T6, T7, T8, T10, T11):** every entry names its venue, its resolved availability facts and its MCP registration state, so the configuration is reconstructable by a stranger.
- **Layer 3 — recountability (T4, T7, T12):** every zero/exactly-once claim states its counting domain and method (AC-2.3, NFR-5). Reproduction = re-count over the quoted transcript or artifact.

Per Must story: **US-1** — layer 1 baseline + layer 2 silence run, negative case before any positive claim (constitution §4). **US-2** — layer 2 full run in a layer-1-verified fixture, layer 3 count. **US-3** — layer 2 twice on the MCP branch and once on the CLI branch, bracketed by layer-1 registration evidence. **US-4** — T9 is deliberately documentation-level only and labelled so; the live proof is layer 2 on `V-PAGE`, once per backend. Nothing is deferred to a later `/demo-day`: US-4's minimal navigate-plus-assert *is* the browser layer, by design (spec §6 cuts a full product QA).
