## 1. Architecture Decision

- **Context:** The spec is retrospective and its own *Gaps* section closes G1 and G2 in the working tree; its *Note for planning* states that what remains "is not spec work but **proof**". So no task here may touch `lenses/`, `agents/`, `skills/` or `templates/` — the deliverable is written evidence. Constitution §3 allows no new tracked executable code; §4 rules out a test suite and sets the bar at a documented dogfood or dry run, **negative case first** (§1); §8 defines a performed step as a real ceremony invocation or an observed command output, never a read-and-reason. Four projects on this machine carry a `.spark/constitution.md` with a §2 profile; three are other people's repos, two of them private, and this repo's `.spark/` is published (§5, §6) — so the evidence artifact is a publication.
- **Decision:** One ledger, `.spark/situational-lenses/evidence.md`, with three evidence classes, each labelled per row so a reader can tell them apart:
  1. **Artifact audit (this repo, public, quotable verbatim)** — the 8 lens files, `lenses/README.md`, the skills' lens-passing form. Reproduction = re-running the quoted read-only command.
  2. **Performed run (live, in a disposable scratch venue outside every real repo)** — the no-constitution nudge case first, then the constitution-present control. These are the only ceremony invocations; nothing is run inside a surveyed project.
  3. **Field evidence (completed loops in profiled projects)** — the artifacts of loops that already ran are the *output* of a performed ceremony, not a thought experiment, and are admitted as such; each row states the project id, the artifact kind, the spec ID, and the phase. Field evidence is never relabelled as a performed run.

  Every row carries exactly one verdict from a fixed vocabulary: `confirmed (audit)`, `confirmed (performed)`, `confirmed (field)`, `refuted-with-finding`, `not-verified-live (venue named)`. Extraction of class 3 is by **hand-run read-only `grep`/read whose command is quoted in the ledger** — no scanner, not even an untracked one. **Privacy rule (binding, not an afterthought):** surveyed projects appear only as opaque ids (`P1`–`P3`, plus `P-SELF` for this repo); the ledger records lens names, phase names, `AC-n.m`/`NFR-n` shapes, category labels, counts and verdicts — and **zero** verbatim text, file paths, project names or feature names from any non-public repo. The id↔project map lives in an untracked scratch note, never committed. Same trade, same reasoning as `docs/reports/` (`docs/reports/README.md`: "Opaque ids and counts. No project name, no feature name, no hostname, no path").
- **Alternatives considered:**
  | Alternative | Why rejected |
  |---|---|
  | One-off untracked scanner over the four repos, output committed (allowed by §3) | Every row needs a judgement a parser cannot make — is this NFR *lens-attributed* or the template's standing Accessibility row? — so the scanner's output would still be read by hand, and it adds code to verify plus a post-hoc anonymization pass that is the likeliest way to leak. Hand-run greps with quoted commands are recountable and leak-proof at the point of writing |
  | Build a synthetic `website`+`seo` fixture venue so AC-2.1 can pass live | It would prove the *mechanism* fires, not AC-2.1's claim ("on a `website` feature"). Presenting a fixture pass as AC-2.1 satisfied is exactly the R1 failure the spec names — a lens that never fired in the field looking identical to one that did. The literal AC lands `not-verified-live` with the missing venue named |
  | Run a fresh `/story-time` inside the profiled projects to generate first-party evidence | Writes into other people's repos (two private), and it is unnecessary: loops that already completed under an active profile carry the evidence. Precedent: `.spark/graph-gates-verification/plan.md` §1, no writes into user repos |
  | Fix the gaps the sweep surfaces (e.g. any hard-coded lens enumeration) inline | Breaks the verify-only fence: repair widens the diff and converts a refutation into a change. Findings route to a later increment, per `CLAUDE.md`'s refuted-with-finding ceremony |
  | Skip the live runs and survey only | US-4's nudge-only behaviour postdates G1's closure, so **no** completed loop anywhere exercises it; and §1 demands the negative case be run, not inferred |
- **Consequences:** Easier — the fence is auditable by `git diff`, every count is recountable from its quoted command, and both a refutation and a missing venue have a pre-built landing place, so no row has to be forced. Harder — the privacy rule costs the evidence its verbatim quotes for class 3, which weakens a finding to "id + spec ID + characterization" and pushes the quote into an untracked note only the operator can see; and two fresh scratch sessions are real spend.

## 4. Test Strategy

No automated test exists or is possible for prompt material (constitution §4), and the spec cut automated enforcement consciously (§6). For this feature the ledger **is** the test suite, in three layers that mirror §1's evidence classes:

- **Layer 1 — artifact audit with quoted commands (T1–T3, T12):** every number reproducible by re-running the quoted read-only command. This is the only layer that may quote verbatim, because its subject is this public repo.
- **Layer 2 — performed ceremony runs (T4, T5):** the negative case first, per constitution §1 — a scratch project without a constitution must produce a nudge and change nothing. These are the only two invocations; each entry names its venue and session state so the configuration is reconstructable. This is also the one layer where §8's "performed step" bar is met in the strict sense.
- **Layer 3 — field evidence from completed loops (T6–T10):** the subject is a ceremony that already ran; the check is whether the same `AC-`/`NFR-` ID appears in the downstream artifact that was supposed to carry it. Recountable by re-running the extraction grep against the same trees.

**Deliberately left to `not-verified-live`, with the reason stated in the row, not implicitly:** AC-2.1 (`seo` NFR on a `website` feature, QA-verified) and the `api`-typed half of the Review leg. No project reachable on this machine declares type `website` or `api`, and none activates `seo`; the honest record is a named missing venue. A purpose-built fixture is rejected in §1 — it would prove the mechanism and be filed as the claim.

**How the next two gates re-verify, given there is no code diff:**
- **`/peer-review`** reviews the *evidence*, not an implementation: for each row, does the stated verdict follow from the quoted command or named artifact; is the counting method stated wherever a zero or an exactly-once is claimed (the single biggest failure mode here — a zero that merely means "nothing was looked at"); is every class-3 row labelled as field evidence rather than as a performed run; does the privacy denylist grep come back empty; and does `git diff --name-only` confirm the fence. A row whose verdict outruns its evidence is a finding against NFR-2's traceability bar.
- **`/demo-day`** runs under §8's substitute method (no browser-observable surface here). Its performed step is re-execution, not reading: re-run a sample of the quoted Layer-1 commands and confirm the ledger's numbers, and re-run the Layer-2 negative case in a fresh scratch venue to confirm the nudge-only behaviour independently. Rows it cannot re-execute — every Layer-3 row, because the loop that produced it cannot be re-run — are marked `not-verified-live` in `qa.md` with the field-evidence pointer, exactly as §8 requires for anything that was read rather than performed.
