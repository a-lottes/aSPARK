## 1. Architecture Decision

- **Context:** Two halves, two different seams, both already present. `skills/story-time/SKILL.md` is a dispatcher that resolves inputs (lenses, template paths, constitution) *before* delegating, and `agents/product-owner.md` holds `Read, Grep, Glob, Write` — no `Bash`. `skills/go-live/SKILL.md:30-32` already hands `.spark/constitution.md`'s `Delivery & Handoff` section to `release-manager`, whose step 2 (`agents/release-manager.md:53-59`) reads that declaration and whose step 6 (`:89-99`) already performs irreversible outward-facing `gh` actions, but only after the caller relays step 4's explicit go. Nothing new has to be invented; the work is placing two calls at the two seams that already exist, and making the second one structurally unrepeatable.

- **Decision:**
  1. **Read, at the dispatcher.** `/story-time` gains one optional argument. When an issue number is passed, a new step runs `gh issue view <n> --json number,title,body,url` at the skill level — the same level that already runs orchestration shell — and feeds the fetched title/body/URL into step 3's existing "the user's idea verbatim" slot, with the delegation sentence extended so the PO cites the reference in the spec's existing `Ticket` row and states the seeding once in §1 (AC-1.2). No agent tool grant changes (A7); no `tools/gh.md` (A5). The repo is resolved **once** per run, before the fetch, from `origin` (A6), echoed to the user, and a repo that cannot be resolved unambiguously (no `origin`, or several remotes and no `origin`) is an AC-1.3 stop, not a guess.
  2. **Write, at the existing declaration seam.** One new `templates/constitution.md` §7 bullet — `Tracker write-back: github-issues-comment | none`, default `none` — inserted between `Ticket-reference format` and `Terminal status` (`templates/constitution.md:97-98`), because it fires at the same handoff point (A2). `/go-live` step 2's existing sentence is extended to name it; `release-manager` reads it where it already reads §7 (step 2), lists the pending comment among step 6's pending commands so step 3's release plan names it (AC-2.6), and performs it **only** in the post-go branch.
  3. **Exactly once, ever — four structural constraints, not a promise.**
     **(a) Capability locality:** `gh issue comment` is named in exactly one file in the plugin, `agents/release-manager.md`, inside one branch. No other ceremony or agent is granted the action, so "a later ceremony re-posts" (AC-2.7) cannot happen by construction — the capability is not there to invoke.
     **(b) Trigger locality:** the call sits beside push/PR/deploy in the post-go branch, so it is covered by the same relayed authorization (AC-2.6, NFR-6) and there is physically no call site on the prepare-only path.
     **(c) Idempotence anchor:** before posting, `release-manager` reads its own `.spark/<feature>/release.md` §3 Release Actions for a `Ticket comment` row with a posted result; present → skip and record "already posted, not repeated". The artifact is the idempotency key — durable, in-repo, and readable **without** asking the tracker anything (§6, one direction only).
     **(d) Terminal-status precondition:** only `released`, `handed-off`, `aborted` — never `preparing` (C3), so a prepared-but-unpublished run leaves the tracker untouched.

- **Alternatives considered:**
  | Alternative | Why rejected |
  |---|---|
  | Ship a `tools/gh.md` ambient-probe file with the four-state hint table | The `tools/` apparatus exists for enrichment *nobody asked for*, which is why it degrades to silence. Here the user's own argument (or declaration) is the ask, so silence would hide an explicit failure — A5/C2, and spec Out of Scope names it |
  | Grant `agents/product-owner.md` a `Bash` tool so the agent fetches its own ticket | Widens one role's permanent blast radius for a single call the dispatcher can already make. A tool grant is forever and applies to every `/story-time` run; A7 rules it out, NFR-2 measures it |
  | Comment at each gate (spec approved, review passed, QA passed) rather than once at terminal close | Explicit Out of Scope and C3: `preparing` means nothing concluded, and running commentary is exactly what the ROADMAP's "one direction only" rules out. Also multiplies R4's uncorrectable-write surface by four |
  | Let §7's existing `Ticket-reference format` authorize write-back too (one field, not two) | C1: an ID *shaped* like GitHub's says nothing about wanting an outward action taken against someone's tracker. Conflating them silently authorizes a side effect |
  | Guarantee once-ever by reading the issue's existing comments before posting | Requires reading tracker state back — forbidden outright by §6 and the spec's own Out of Scope. The `release.md` row gives the same guarantee with zero reads |
  | A new §10 `Tracker Integration` constitution section instead of extending §7 | A2 ruled it: same handoff point, same lifecycle, same reader. A new section costs every existing project a heading it will never fill |
  | A new `/ticket` command or a per-feature spec-level override of the mode | NFR-2 (zero new commands) and Out of Scope (the constitution declares once; a spec does not re-declare) |

- **Consequences:** *Easier:* the comment inherits an authorization ceremony that already exists, so no second confirmation step is added (NFR-6); both halves are pure prose edits to four files, no protected structure touched (NFR-1); an undeclared project's code path is unchanged because both entries are guarded by an absent argument / absent field. *Harder:* the write half's positive case cannot be proven on this repo at all (§7 here says `Ticket-reference format: none`), so T9 stands up and tears down a scratch repo — real infrastructure work for one observation; `release-manager`'s step 6 grows a branch in an already dense file; the idempotence key lives in a hand-editable artifact, so a user who deletes the row can re-post (accepted, same shape as R4).

- **Scope check (constitution §3, CLAUDE.md's "every phase the artifact claims").** The new §7 field is written by `/charter` only. Verified that no file outside spec §5's touched list enumerates §7's fields in closed form: a repo-wide grep over `skills/`, `agents/`, `templates/` for `Ticket-reference|Delivery & Handoff|Release mode` returns only `agents/release-manager.md:54`, `skills/go-live/SKILL.md:31` and `templates/constitution.md:88-98`, and `agents/facilitator.md:60-64` drafts from `templates/constitution.md` generically (first draft) or preserves-and-amends (existing file). So the field propagates without touching `/charter`'s own files. No plan-time change needed there.

## 4. Test Strategy

No automated suite exists and none is possible for prompt material (constitution §4) — do not add one. The bar per task is `claude plugin validate .` plus a documented dogfood or dry run of every phase touched, **negative case first**, written into `.spark/ticket-import/evidence.md`. `/demo-day`'s browser gate is N/A (§8: no browser-observable surface); its substitute is hands-on invocation of the installed plugin, where a performed step is a real ceremony run or a real observed command output — reading a Markdown file and reasoning about what it *would* do never passes an AC.

- **US-3 (Must, the dominant risk) — T1, T4, T8.** Full before/after diff on this repo: same steps, sections and gate boxes, and the grep counts for "ticket"/"tracker"/"write-back" recorded at T1 must still hold at T8. T1 runs before any edit, which is what makes AC-3.3 provable rather than asserted.
- **US-1 (Must) — T4, live, on this repo's own public issue #19.** Read-only, draft to an untracked scratch path. Happy path (AC-1.1/1.2/1.4) plus at least one real failure (AC-1.3) observed, not described. AC-1.5's privacy statement is verified by its presence in the live transcript before the write, not by reading the skill file.
- **US-2 (Should) — T9, in the scratch repo, because it cannot be proven here** (§7 declares `Ticket-reference format: none`, and amending that is `/charter`'s call, not this feature's). The load-bearing observation is the *count*: exactly one comment after the terminal run, still one after a deliberate re-run (AC-2.7). AC-2.3's skip path is provable on this repo cheaply by running with `gh` unauthenticated or the field set in a scratch constitution pointed at a nonexistent issue.
- **Deliberately not run live:** AC-2.5 (`Ticket: none` with write-back declared) is verified by reading the release plan output of a prepare-pass, since there is nothing to observe on a tracker by design. NFR-1, NFR-2, NFR-7, NFR-8 are `/peer-review` diff checks — nothing executes.

## 5. Risks & Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| **R1 (spec)** — `gh` availability/auth drifts between machines | A fetch or post fails on a machine that differs from the one where the ticket was authored | AC-1.3 stops and reports for the read half; AC-2.3 skips and records for the write half. No gate ever blocks on it (NFR-5). Not solved — named |
| **R2 (spec)** — GitHub API rate limits | A call fails for a reason unrelated to the feature | Accepted risk, per spec: one or two calls per feature is orders below any real limit. Failure lands in the same reported-skip path as R1 |
| **R4 (spec)** — write-back is an uncorrectable escape hatch | An `aborted` comment posted, then the team ships anyway; nothing corrects the tracker | AC-2.7 makes the risk visible rather than hidden (one write, ever, and no edit path). Same shape and same non-solution as `tracker-handoff`'s R1 |
| **P1 (new)** — the scratch repo (T9) cannot be created: `gh repo create`/`gh repo delete` may need scopes beyond current auth (`delete_repo` in particular), or the user may decline at that moment | US-2 has no positive-case venue, so the write half stays unproven | T9 is its own task, so this fails visibly and early instead of mid-way through another task. If it fails: the write half ships **disclosed as unproven** and `ROADMAP.md` keeps it out of Shipped (NFR-9, T10) — a refuted-with-finding outcome, not a ground-it-out one |
| **P2 (new)** — `origin` resolves ambiguously: a fork (issue numbers belong to the fork, not upstream), or several remotes with no `origin` | The read fetches the wrong repo's issue; worse, the write posts a comment to a stranger's tracker | Decided in §1: resolve once, echo the resolved `owner/repo` to the user before the fetch and before the post, and treat unresolvable/ambiguous as an AC-1.3 stop. Cross-repo references stay out of scope (A6), so no `owner/repo#n` form widens this |
| **P3 (new)** — the idempotence key is a hand-editable artifact row | Deleting or editing `release.md` §3's `Ticket comment` row re-enables a second post | Accepted, and it is the lesser evil: the alternative key is reading tracker state, which §6 forbids outright. Capability locality (§1.3a) still bounds it to `/go-live` |
| **P4 (new)** — the docs run ahead of the evidence | `README.md`/`ROADMAP.md` claim Shipped while T9 is unproven — exactly the constitution §1 defect | T10 depends on T9 and its DoD requires each claim to trace to a recorded run; read and write maturity are named separately, never as one capability |
| **P5 (new)** — already-installed consumer projects never get the new §7 field | Their constitutions have no `Tracker write-back` line | Not a defect: absent ⇒ `none` ⇒ byte-identical behavior (AC-2.4, NFR-4). Adding the field to an existing constitution is `/charter`'s amendment path, which `agents/facilitator.md:60-64` already handles generically |
